# 구조화 전형 모드 — 경험기술서·문답형 상세지원서

cover-letter 스킬 SKILL.md Phase 0 에서 전형 형식이 경험기술서/문답형으로 확인되면 Read 한다.

---

## §0. 전형 형식 확인 규칙

기업별 전형 형식은 이 문서에 하드코딩하지 않는다. **실행 시 공고·지원서 양식에서 직접 확인**한다 — 특정 기업이 어떤 형식을 쓴다고 단정하지 않는다(guardrails §5 — 시간에 민감한 기업·전형 정보는 실시간 확인 없이 단정하지 않는다).

Phase 0 에서 D) 구조화 전형이 선택되면, 다음 질문으로 세부 모드를 확정한다:

```
현재 상황: 지원서 문항이 일반 자소서(항목당 자유 서술)와 다른 구조로 보입니다.
질문: 공고·지원서 양식을 확인했을 때 어느 쪽에 가깝나요?
추천: A) 경험기술서. 이유: 문항이 소수(3~6개 내외)이고 항목명이 "직무 전문성/문제 해결/AI 활용"류면 경험기술서에 가깝습니다.

A) 경험기술서 — 문항별 장문 서술, 항목당 글자수 제한
B) 문답형 상세지원서 — 짧은 답변 수십 문항
C) 아직 미확인 — 공고·지원서 화면 문구를 붙여넣어 주시면 바로 판별합니다
```

A → §1·§2 적용. B → §3 적용(§1·§2 는 문항별로 필요한 부분만 준용). C → 자료 요청으로 전환(guardrails §2), 자료 확보 후 재질문.

## §1. 경험기술서 모드

경험기술서·경력기술서의 정의 자체는 `three-docs-guide.md` §2 가 단일 소스다 — 여기서는 cover-letter 가 경험기술서 **문항에 초안을 쓰는 절차**만 다룬다.

### 문항 유형

| 문항 유형 | 평가 기준 |
|---|---|
| 직무 전문성 경험 | 직무 관련 실력의 깊이와 근거 |
| 문제 해결 경험 | 문제 정의력과 해결 과정의 논리 |
| AI·도구 활용 경험 | 도구를 과업에 맞게 쓰고 검증한 판단력 (§2 적용) |
| 협업·갈등 | 이해관계 조율과 본인의 판단 |
| 실패·학습 | 실패 원인 분석과 이후 행동 변화 |

문항 의도가 모호하면 cover-letter Phase 3 문항 의도 추출 절차를 그대로 적용한다.

### 결이요 대신 4분리 우선

경험기술서 문항은 평가 기준이 이미 좁게 특정돼 있어, 결(론)의 "차별화 선언"이나 요(청)의 "지원 부서 연계 비전"이 오히려 글자수만 소모하는 경우가 많다. **문제·역할·행동·결과 4분리**(`experience-methods.md` §2)를 문항당 **1경험**으로 우선 적용한다 — 여러 경험을 한 문항에 섞지 않는다. 지원동기·포부성 문항이 섞여 있으면 그 문항만 결이요로 되돌린다.

### 수치 규칙

수치가 없으면 `experience-methods.md` §3 **대체 4종**(범위·빈도·전후 비교·담당 규모)을 우선 적용한다. 대체 근거도 없으면 수치를 만들지 않고 `[수치 확인 필요]`로 남긴다(guardrails §1 — 항목당 1회만 질문, 미응답 시 유지).

### 문항별 글자수 게이트

- 공백 포함/제외 기준은 **양식에서 먼저 확인**한다(임의 가정 금지 — 시스템마다 정의가 다르다).
- 목표는 한도 대비 90~100% 채움이 기준이다.
- 초과분 삭제 우선순위: ① 수식어 → ② 배경 설명 → ③ 중복 근거. 4분리 문장(문제/역할/행동/결과) 자체는 최후까지 유지한다.
- 측정 명령 — 초안을 표준입력으로 넣으면 포함/제외 값을 함께 출력한다. "제외"는 스페이스만 뺀 값과 개행·탭·전각공백까지 뺀 값 두 가지를 내며, 폼마다 정의가 다르므로 지원 폼의 카운터 값이 있으면 그 값을 우선한다:

```bash
python3 -c "import sys, re; s=sys.stdin.read().rstrip(); print('포함:', len(s), '| 제외(스페이스만):', len(s.replace(' ', '')), '| 제외(개행·탭·전각공백 포함):', len(re.sub(r'\\s', '', s)))"
```

### 경험뱅크 카드 재사용 순서

0. 지원 기업과 `apply_plans[].company` 가 일치하는 카드(`jobstack-exp.mjs list --company <기업명>`) 우선 — 4분리 문항(직무 전문성·문제 해결·협업·실패)에서는 R 문장을 본문에 쓰지 않고 카드 선택 근거로만 쓰며, 지원동기·포부성 문항에만 R(experience-methods.md §7)을 잇는다.
1. `job_link_tags` 가 문항 성격과 일치하는 카드 우선.
2. AI·도구 활용 경험 문항이면 `ai_usage` 필드가 채워진 카드 우선 — 없으면 §2 지침대로 그 자리에서 보강 질문.
3. 후보가 여럿이면 `numbers`(수치)가 채워진 카드 우선, 정성만 있는 카드는 후순위.
4. 적합한 카드가 없으면 `experience-methods.md` §1 6단계로 즉석 인터뷰한다. 카드 저장 자체는 experience-bank 스킬 담당이므로, 여기서는 초안에만 쓰고 저장 여부는 사용자에게 안내한다(경계 준수).

### 출력 형식

```
문항 1. [직무 전문성 경험] (제한: 공백 포함 800자 — 양식 확인값)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[초안 본문]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
글자수: 포함 782 / 제외 705 (한도 대비 98%)
4분리 체크: 문제 ✓ 역할 ✓ 행동 ✓ 결과 ✓
미끼 포인트: "[핵심 수치·기술 선택 문구]" → 예상 질문: "..."
```

## §2. AI·도구 활용 경험 문항

4요소 — 하나라도 비면 `[확인 필요]`로 남기고 그 요소만 질문한다:

| 요소 | 채울 내용 | 소스 |
|---|---|---|
| 도구명 | 실제 사용한 도구·서비스 | 카드 `ai_usage.tool` |
| 과업 | 그 도구로 처리한 구체 업무 | 카드 `ai_usage.task` |
| 검증 방법 | 출력 결과를 본인이 어떻게 확인·수정했는지 | 없으면 `[확인 필요]` |
| 전후 변화 | 도구 사용 전/후 비교(정성 가능) | 카드 `ai_usage.effect`, 없으면 §1 수치 규칙 적용 |

**금지**: "AI가 다 했습니다", "AI 덕분에 쉽게 끝냈습니다"처럼 검증 과정이 없는 서술은 쓰지 않는다. 무엇을 채택·수정·기각했는지 본인의 판단을 최소 한 문장 포함한다 — 근거 없는 서술은 Phase 8 위험 문장 테스트에서 위험 문장으로 분류될 가능성이 크다.

## §3. 문답형 상세지원서 모드

### 절차

1. **문항 목록화** — 전체 문항을 순번·문항명·글자수 제한 표로 정리한다.
2. **카드 배정표** — 문항마다 사용할 경험 카드 id를 배정한다(§1 재사용 순서 적용).
3. **초안** — 문항별로 §1 4분리를 적용해 작성한다.
4. **일관성 검사** — 아래 체크리스트로 문항 간 사실을 대조한다.
5. **글자수** — §1 게이트를 문항별로 재적용하고 표로 일괄 출력한다.

### 답변 간 사실 일관성 검사

같은 경험 카드가 배정된 문항들을 모아 다음 항목을 대조한다. 충돌은 **원 카드(`experiences.yaml`) 기준으로 통일**한다.

| 대조 항목 | 확인 방법 | 충돌 시 처리 |
|---|---|---|
| 기간 | 문항마다 개월·연 수 표현이 같은지 | 카드 값으로 통일 |
| 수치 | before→after 값이 문항마다 같은지 | 카드 `numbers`/`change` 값으로 통일, 근거 없는 값은 재확인 |
| 역할 범위 | "전체 담당" 대 "일부 담당" 표현이 같은지 | 카드 `role` 값으로 통일 |
| 도구 | 사용 도구명이 문항마다 같은지 | 카드 `ai_usage.tool`/`action` 값으로 통일 |
| 회사명 | 재직 회사명 표기(축약/전체)가 같은지 | 프로필 표기로 통일 |
| 팀 규모 | 인원 수 표현이 문항마다 같은지 | 카드 `numbers` 값으로 통일, 근거 없으면 정성 표현으로 완화 |

문서 간(이력서↔자소서 등) 정합성은 이 스킬이 아니라 `/review`가 담당한다(`three-docs-guide.md` §4) — 여기서는 **같은 문서 내부 문항 간** 일관성까지만 책임진다.

### 반복 소재 상한

같은 경험 카드는 **최대 2문항**까지만 배정한다. 2문항에 쓸 때는 카드 배정표에 각 문항이 4분리 중 어느 요소를 주로 부각하는지 표시해 관점을 분리한다 — 같은 문장을 두 문항에 반복하지 않는다.

### 출력 형식

```
문답형 상세지원서 — 전체 42문항 / 카드 배정 완료 38 / 배정 대기 4
카드 배정표 (일부)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
문항#  문항명              카드id           강조 4분리 요소
3      팀워크 경험          exp-...-02       역할·행동
17     같은 경험, 다른 관점  exp-...-02       결과
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
[문항별 초안 → 글자수 → 4분리 체크는 §1 출력 형식과 동일 반복]

일관성 검사 결과
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
대조 항목   충돌 문항        처리
수치        #12 ↔ #29        카드 기준으로 #29 수정
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## §4. 완료 상태 판정 추가 규칙

cover-letter 완료 상태 판정(SKILL.md 하단)에 다음을 더한다 — 기존 기준을 대체하지 않는다:

- §1 글자수 게이트를 통과하지 못한 문항이 하나라도 남으면 → **DONE_WITH_CONCERNS** (우려사항에 미통과 문항 번호를 명시)
- §3 일관성 검사에서 해소되지 않은 충돌이 있으면 → **DONE_WITH_CONCERNS** (우려사항에 충돌 항목·문항 쌍을 명시)
- 두 조건에 모두 해당하면 우려사항을 항목별로 모두 나열한다(하나로 뭉뚱그리지 않는다).
